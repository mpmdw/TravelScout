## 1. Mission

Replace the hand-drawn ~22-point Iran outline with a **real, documented Tehran FIR (OIIX)
boundary** committed to the repo as GeoJSON with provenance metadata, loaded through a small
ingestion layer that keeps the zone list user-configurable and leaves room for future
closures/advisories feeds. The "approximate / not for operational use" disclaimer stays.

## 2. Context — what exists today

- `src/lib/dangerZones.ts` exports `DANGER_ZONES: DangerZone[]` — one hardcoded zone
  (`id: "iran-fir"`) whose `polygon` is a coarse open ring of `[lng, lat]` pairs
  (`dangerZones.ts:21-44`), plus a commented example zone.
- `DangerZone` type (`src/lib/types.ts:17-24`): `{ id, name, severity: "avoid"|"caution",
  reason, polygon: [number,number][] }` — **single outer ring, open** (closed automatically
  by `closeRing` in `geo.ts:7-12`).
- Consumers: `geo.ts` (`zonePolygon` at `:14` builds `turf.polygon([closeRing(...)])`),
  `/api/zones` (returns the raw list), `/api/route` and both flight providers (pass
  `DANGER_ZONES` to `planRoute`), `MapView.tsx:52-61` (draws `z.polygon` directly).
  **Keeping the `DangerZone` shape unchanged means zero consumer edits.**
- README has a "Configuring danger zones" section pointing at this file.

## 3. Non-goals

- No live/auto-updating closure feed (explicitly "Future / out of scope" in the roadmap —
  this task only *structures the data so it can be ingested later*).
- No multi-ring/MultiPolygon support in the runtime `DangerZone` type (the ingestion layer
  flattens; see decision 4).
- No change to avoidance behavior (P2.3).

## 4. Design decisions (pre-made)

1. **Source**: FIR boundaries from an open, attributable dataset. Recommended (in order):
   1. **VATSpy Data Project** (`github.com/vatsimnetwork/vatspy-data-project`,
      `Boundaries.geojson`) — community-maintained real-world FIR outlines, widely used,
      easy to extract one FIR by ICAO id (`OIIX`).
   2. ICAO/FAA published FIR shapefiles, if a directly downloadable GeoJSON is found.
   The executing agent should verify the chosen source's current URL + license terms and
   record both in the metadata file. If VATSpy licensing is unclear for this use, fall back
   to tracing the FIR from official ICAO charts and say so in the metadata (still better
   provenance than "hand-drawn").
2. **Repo layout** (new):
   ```
   data/airspace/
     oiix-tehran-fir.json     # GeoJSON Feature (Polygon or MultiPolygon), raw-ish
     SOURCES.md               # per-file: source URL, retrieval date, license, processing steps
   ```
3. **Ingestion at import time, not request time**: a new module
   `src/lib/airspaceData.ts` imports the JSON (Next.js/TS supports JSON imports with
   `resolveJsonModule`; check `tsconfig.json` and enable if missing) and converts
   GeoJSON → `DangerZone`:
   - Take the **outer ring** of the Polygon; for MultiPolygon take the largest-area polygon
     (`turf.area`) — Tehran FIR is contiguous, so this is just defensiveness.
   - **Simplify** with `turf.simplify({ tolerance: 0.05, highQuality: true })` if the ring
     exceeds ~300 points (map drawing + intersection both get slow with thousand-point
     rings; record the applied tolerance in `SOURCES.md`).
   - Drop the closing duplicate point (our convention is an open ring).
4. **`dangerZones.ts` becomes a registry, not data**: it composes the exported list from
   ingested FIRs + (still supported) inline hand-drawn zones:
   ```ts
   export const DANGER_ZONES: DangerZone[] = [
     firZone("oiix", {
       name: "Iran airspace (Tehran FIR)",
       severity: "avoid",
       reason: "Heightened conflict risk / overflight advisories. Many carriers route around Iranian airspace.",
     }),
     // inline zones still work — see the commented example
   ];
   ```
   This keeps the README promise that zones are configured by editing this one file.
5. **Disclaimer stays and gets more accurate**: replace "Coarse outline of Iran (NOT exact
   borders)" wording with "Sourced FIR boundary (see data/airspace/SOURCES.md), simplified;
   still approximate and not for operational use."

## 5. Execution plan

**Step 0 — preflight.** Branch; `npm run build` green.

**Step 1 — fetch the boundary.** Download the dataset, extract the OIIX feature
(`jq`/node script is fine), save as `data/airspace/oiix-tehran-fir.json` as a single
GeoJSON `Feature` with `properties: { icao: "OIIX", name: "Tehran FIR" }`. Eyeball sanity:
ring should span roughly lng 44–63.5, lat 25–40 (compare with the old hardcoded ring at
`dangerZones.ts:21-44` — same neighborhood, more vertices).

**Step 2 — provenance.** Write `data/airspace/SOURCES.md`: source name + URL, retrieval
date (today), license/attribution text, exact processing commands used (so the file is
reproducible), simplification tolerance if applied.

**Step 3 — `src/lib/airspaceData.ts`.** Implement `firZone(id, meta): DangerZone` per
decision 3/4. Validate at load: ring length ≥ 4, all coords numeric, lat ∈ [-90,90],
lng ∈ [-180,180]; **throw at import time** on violation (fail fast at build, not at request).

**Step 4 — rewrite `dangerZones.ts`** per decision 4, preserving: the exported name
`DANGER_ZONES`, the doc-comment explaining how to add zones (update it to mention both
inline rings and `firZone`), and the disclaimer language.

**Step 5 — visual check.** `npm run dev`, plan **London → New Delhi**: the direct path must
still flag the Iran zone, the shaded polygon should visibly hug Iran's borders more closely
than before, and a reroute should still compute. Screenshot for the PR.

**Step 6 — docs + roadmap.** README "Configuring danger zones" section: mention the
`data/airspace/` directory and `SOURCES.md`. Tick P1.4 in the roadmap.

## 8. Edge cases & failure modes

- **The detailed FIR ring defeats the single-waypoint heuristic** (reroute comes back
  `null` for London→Delhi): first try a slightly stronger simplification (the convex
  detail is what matters for avoidance); if it still fails, this is acceptable *only if*
  documented in the PR and P2.3 is noted as the fix — the UI already handles
  `avoidancePath: null` ("Couldn't compute a clear reroute automatically").
- **Antimeridian**: OIIX doesn't cross ±180°, but write the validation to *warn* (not
  throw) if a future ingested FIR does, and note that P2.3 owns antimeridian handling.
- **Ring winding**: turf accepts either winding for a simple polygon ring after
  `closeRing`; don't bother normalizing.
- **JSON import size in the client bundle**: `dangerZones.ts` is imported by API routes
  only; the map gets zones via `/api/zones` fetch (`page.tsx:52-57`), so the GeoJSON does
  **not** ship to the client twice. Verify nothing imports `dangerZones.ts` from a client
  component.
