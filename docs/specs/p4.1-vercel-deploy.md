## 1. Mission

Get TravelScout serving on a live HTTPS `*.vercel.app` URL with production env vars set,
the P3.1 login gate verified in production, preview deployments on PRs, and the README
deploy section updated to match reality.

## 2. Context — what exists today

- Standard Next.js 15 App Router app — **zero Vercel-specific config exists** and none is
  strictly required. `next.config.mjs` carries security headers (P3.2).
- Server features that constrain the platform config:
  - `/api/geo-intel` declares `export const maxDuration = 60` (`geo-intel/route.ts:5`) —
    Claude-with-web-search can take tens of seconds. On Vercel, Hobby-plan functions
    default to shorter limits but `maxDuration` up to 60s is honored with Fluid Compute
    (the current default); **verify the deployed function's limit in the dashboard** and
    document the observed cap in the README.
  - All API routes are `dynamic = "force-dynamic"` — no ISR/caching surprises.
  - In-memory caches/rate-buckets (P2.2/P3.1) are per-instance — already documented as
    best-effort; no action, but worth re-stating in the deploy README section.
  - Middleware (auth gate) runs on the edge — works on Vercel out of the box.
- Env vars the deployment needs (server-only, from `.env.example`):
  `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`, `AMADEUS_CLIENT_ID`, `AMADEUS_CLIENT_SECRET`,
  `AMADEUS_HOSTNAME` (**flip to `api.amadeus.com` only if production Amadeus access was
  purchased — otherwise keep the test host and live with test-data quirks**),
  `FLIGHT_STATUS_API_KEY`, `FLIGHT_STATUS_PROVIDER`, `NOMINATIM_CONTACT`,
  `BASIC_AUTH_USER`, `BASIC_AUTH_PASS`/`AUTH_PASS_HASH`, `AUTH_SECRET`,
  `GEO_INTEL_CACHE_TTL_MIN`. **Shadow mode (G1) means the app deploys fine with NONE of
  them** — set the auth trio at minimum so the public URL isn't open.
- Repo: private `mpmdw/TravelScout` on GitHub; `gh` CLI not authenticated; git pushes via
  SSH. Vercel's GitHub integration needs the Vercel app granted access to the repo
  (HUMAN, one-time).

## 3. Non-goals

- CI-driven deploys (P4.2 decides Git-integration-vs-Actions; this task uses Vercel's
  built-in Git integration which P4.2 then leans on).
- Custom domain (not roadmap'd; trivially addable later).
- Observability (P4.3), load testing, multi-region.

## 4. Design decisions (pre-made)

1. **Use the Vercel Git integration** (import the GitHub repo in the Vercel dashboard)
   rather than CLI-only deploys: it gives production-on-main + preview-per-PR with zero
   workflow code, which is exactly P4.2's deploy story.
2. **No `vercel.json` unless needed.** Framework auto-detection covers everything; only
   create the file if a real knob demands it (e.g. pinning function `maxDuration`
   project-wide). Document the decision either way in the PR.
3. **Auth before exposure**: set `BASIC_AUTH_USER` + password var(s) + `AUTH_SECRET` in
   the Vercel env **before** the first production deploy of a non-trivial dataset — the
   URL is public the moment it deploys.
4. **Env scoping**: set secrets for *Production* and *Preview* both — preview deploys run
   the same gate (friends/testers hit preview URLs). Use **test-tier** API keys in
   Preview if available (Amadeus test host) to protect quotas.
5. **README**: the existing "B) Deploy to the cloud (Vercel)" section gets replaced with
   the Git-integration flow (CLI flow demoted to an alternative).

## 5. Execution plan

**Step 1 — [HUMAN] Vercel setup.** Create/log into Vercel; *Add New → Project → Import*
`mpmdw/TravelScout`; grant the GitHub app access to the (private) repo. Framework preset:
Next.js (auto). Do **not** deploy yet if prompted — add env vars first (decision 3).

**Step 2 — [HUMAN] Environment variables.** Project → Settings → Environment Variables:
enter the list from §2 (Production + Preview). Generate `AUTH_SECRET` locally
(`openssl rand -hex 32`).

**Step 3 — Deploy.** Trigger the first production deploy (push to `main` or the
dashboard's Deploy button). Record the URL.

**Step 4 — Verify (agent-runnable once the URL exists).**
```bash
U=https://<project>.vercel.app
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' $U/        # 302 → /login (gate on)
curl -s -o /dev/null -w '%{http_code}\n' $U/api/zones               # 401
# login + cookie flow exactly as in p3.1 §7, against $U
curl -sI $U | grep -i strict-transport                              # Vercel + P3.2 headers
# After login: plan London→Delhi in the browser; flights show source:"live" (if keys set);
# geo-intel returns within the function limit (watch for FUNCTION_INVOCATION_TIMEOUT).
```

**Step 5 — Preview check.** Open a trivial PR (this task's README edits qualify); confirm
Vercel comments a preview URL on the PR and the gate works there too.

**Step 6 — README.** Rewrite deploy section: import flow, env var list (pointing at
`.env.example` as the source of truth), function-duration note for geo-intel, per-instance
cache caveat, preview-deploy behavior. Tick P4.1 in the roadmap.

## 8. Edge cases & failure modes

- **Geo-intel exceeding the function limit on Hobby**: the route catches provider errors
  and degrades to mock (G1) *unless the platform kills the function first* — if timeouts
  appear, reduce the SDK `timeout` (P1.3 set 25s/attempt + a ~35s wall-clock guard,
  worst case ≈ 51s) further below the platform cap so our own
  fallback wins the race. This is the most likely production-only bug; test it explicitly.
- **`AMADEUS_HOSTNAME=test.api.amadeus.com` in prod**: test data is stale/sparse — the UI
  will look "wrong" but isn't broken. README notes this; flipping to prod host is a paid
  decision, not a bug.
- **Nominatim from datacenter IPs**: usage policy applies per-IP; with P2.2's cache +
  1 req/s gate we're within bounds at friend-scale. If 403s appear, the geocode returns
  null → 404 envelope ("Couldn't find a location") — acceptable degradation, note for P4.3
  monitoring.
- **Vercel build env**: no env vars are needed at *build* time (all reads are
  call-time per `config.ts` design) — if a build mysteriously bakes a flag, check for
  accidental top-level `getConfig()` calls.
