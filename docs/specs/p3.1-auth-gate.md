## 1. Mission

Replace the shared HTTP Basic Auth gate with a **signed-session cookie login**: a real
login page, HMAC-signed expiring sessions, per-IP brute-force throttling, logout — while
staying *exactly as simple to share with one friend* (still just a username + password in
env vars), and keeping the gate **off** when not configured.

## 2. Context — what exists today

- `src/middleware.ts` (57 lines): if `BASIC_AUTH_USER` **and** `BASIC_AUTH_PASS` are both
  set, every request (matcher `:53-56` excludes only `_next/static`, `_next/image`,
  `favicon.ico`) must carry matching Basic credentials; constant-time-ish compare
  `safeEqual` (`:46-51`); otherwise 401 + `WWW-Authenticate`. Gate off when either var
  is unset (`:20`).
- Middleware runs on the **Edge runtime** → no Node `crypto` module; use **Web Crypto**
  (`crypto.subtle`) for HMAC. `atob` is available (already used at `:25`).
- No login page, no session, no rate limiting, no logout. Credentials are sent on every
  request (base64), and browsers cache them for the realm — can't "log out".
- README "Two ways to host it" section documents the Basic flow and the
  HTTPS-only warning (`README.md:51-71`); `.env.example:29-33` documents the two vars.
- The app posts JSON from the client to `/api/*` (`page.tsx`) — same-origin only; no CORS
  configured anywhere (good — keep it that way).

## 3. Non-goals

- No multi-user accounts, no OAuth/passkeys, no database (roadmap keeps "simple to share
  with one friend"; user accounts are explicitly in the roadmap's Future bucket).
- No CSRF token machinery: the only state-changing authed action is login itself;
  mitigate with `SameSite=Lax` + same-origin checks, documented below.
- No password-reset flows.
- Security headers/CSP belong to P3.2 — don't add them here.

## 4. Design decisions (pre-made)

1. **Gate activation**: gate is ON iff `BASIC_AUTH_USER` && (`BASIC_AUTH_PASS` ||
   `AUTH_PASS_HASH`) && `AUTH_SECRET` are set. If user/pass are set but `AUTH_SECRET`
   is missing, **fail closed for pages with a clear 500 message** ("Gate misconfigured:
   set AUTH_SECRET") rather than silently disabling — a misconfigured gate must never
   mean an open app. Keep the existing var names (`BASIC_AUTH_USER/PASS`) so current
   deployments keep working — README gets a note that the names are historical.
2. **Password storage**: support both `BASIC_AUTH_PASS` (plaintext env — fine for the
   one-friend case, document the tradeoff) and `AUTH_PASS_HASH` (SHA-256 hex of the
   password — *not* bcrypt because Edge runtime lacks it and the threat model is a
   shared-secret gate, not a credential database; state this tradeoff in a comment).
   If both set, hash wins. Provide the one-liner in `.env.example`:
   `node -e "crypto.subtle.digest('SHA-256',new TextEncoder().encode('pw')).then(b=>console.log(Buffer.from(b).toString('hex')))"`.
3. **Session token** (in `src/lib/auth.ts`, Web-Crypto only so middleware can import it):
   `payload = base64url(JSON.stringify({ u, exp }))`, `sig = base64url(HMAC_SHA256(AUTH_SECRET, payload))`,
   cookie `ts_session=${payload}.${sig}`; `HttpOnly; Secure; SameSite=Lax; Path=/;
   Max-Age=604800` (7 days). Verify = recompute HMAC (constant-time compare) + `exp` check.
4. **Login flow**: `GET /login` (a minimal client page with the existing `.card`/`.input`
   styles) → `POST /api/auth/login {username,password}` → verify (constant-time) →
   `Set-Cookie` → client navigates to `/`. `POST /api/auth/logout` clears the cookie.
   Middleware: requests without a valid cookie → pages **redirect 302 to /login**
   (carrying `?next=` path), API routes → `401 { error: "Authentication required." }`.
   `/login` + `/api/auth/login` are exempt from the gate (obviously), as are the static
   exclusions already in the matcher.
5. **Brute-force throttling** (in-memory, per middleware/route instance — documented
   best-effort, same caveat as all our caches): token bucket per IP
   (`req.headers.get("x-forwarded-for")?.split(",")[0] ?? "local"`): max **5 failed
   logins per 15 min**; further attempts → `429 { error: "Too many attempts. Try again later." }`
   with `Retry-After`. Successful login resets the bucket. Lives in `auth.ts`.
6. **Migration**: drop Basic-Auth header support entirely (one auth path = smaller attack
   surface). README replaces the Basic instructions with the login-page flow; the
   cloudflared/ngrok sharing recipe stays, now with three env vars.

## 5. Execution plan

**Step 0 — preflight.** Branch; build green. Read current `middleware.ts` fully.

**Step 1 — `src/lib/auth.ts`** (pure, Edge-safe, no Node imports):
`createSessionCookie(user, secret, now?)`, `verifySessionCookie(cookieValue, secret, now?)`,
`verifyPassword(input, { pass?, passHash? })`, `loginRateLimiter` (token bucket),
`timingSafeEqualStr` (move/adapt `safeEqual` from middleware). All take `now` injectable
for tests.

**Step 2 — tests (`tests/auth.test.ts`)** — before wiring the app: round-trip
sign/verify; tampered payload/sig rejected; expired rejected; clock-skew tolerance (±0);
password verify for both plaintext and hash modes; rate limiter allows 5, blocks 6th,
resets on success and after window.

**Step 3 — login/logout routes + page** per decision 4. The login page is a small
`"use client"` form (username, password, error line, submit) reusing `globals.css`
classes; on success `window.location.assign(next || "/")`. Validate the body with the
P2.1 helper if merged, else inline checks.

**Step 4 — middleware rewrite.** Keep the file's role: read config → exempt paths →
verify cookie → allow / redirect / 401 per decision 4, fail-closed per decision 1.
Update the matcher to also exclude nothing new except confirming `/login` is handled via
an in-function exemption list (`PUBLIC_PATHS = ["/login", "/api/auth/login"]`), not the
matcher (matcher regexes are hard to review).

**Step 5 — docs.** `.env.example`: add `AUTH_SECRET` (with `openssl rand -hex 32`
suggestion) + `AUTH_PASS_HASH` (+ hash one-liner); README: update gate sections (quick
start, hosting A/B, config table), note the rename-free migration and that existing
`BASIC_AUTH_*` deployments need only to add `AUTH_SECRET`.

**Step 6 — roadmap.** Tick P3.1.

## 6. Acceptance criteria

- [ ] Gate off (no vars): app fully open — byte-identical behavior to today.
- [ ] Gate on: unauthenticated page → `/login`; unauthenticated API → 401 JSON; valid
      login sets `HttpOnly Secure SameSite=Lax` cookie; logout clears it.
- [ ] 6th failed login within 15 min → 429 with `Retry-After`.
- [ ] Tampered/expired cookies rejected (unit-tested).
- [ ] Misconfiguration (user/pass set, `AUTH_SECRET` missing) fails **closed** with a
      clear error.
- [ ] `npm test` + build green; README/.env.example updated (G3).

## 7. Verification

```bash
npm test && npm run build
BASIC_AUTH_USER=friend BASIC_AUTH_PASS=pw AUTH_SECRET=$(openssl rand -hex 32) npm run dev & sleep 5
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' localhost:3000/            # 302 → /login
curl -s -o /dev/null -w '%{http_code}\n' localhost:3000/api/zones                   # 401
curl -si -X POST localhost:3000/api/auth/login -H content-type:application/json \
  -d '{"username":"friend","password":"pw"}' | grep -i set-cookie                    # ts_session=…; HttpOnly; …
C=$(curl -s -X POST localhost:3000/api/auth/login -H content-type:application/json \
  -d '{"username":"friend","password":"pw"}' -c - | awk '/ts_session/{print $NF}')
curl -s -o /dev/null -w '%{http_code}\n' -H "Cookie: ts_session=$C" localhost:3000/api/zones  # 200
for i in 1 2 3 4 5 6; do curl -s -o /dev/null -w "%{http_code} " -X POST \
  localhost:3000/api/auth/login -H content-type:application/json \
  -d '{"username":"friend","password":"wrong"}'; done; echo                          # 401×5 then 429
# Gate-off check: restart with no env vars → / returns 200 with no redirect.
```

## 8. Edge cases & failure modes

- **`Secure` cookie over plain-http localhost**: browsers exempt `localhost` — fine. But
  curl-based dev flows and tunnels are https anyway; don't add an env toggle.
- **Serverless rate-limit reset**: each lambda instance has its own bucket — documented
  best-effort (same caveat as caches). Still raises the cost of dumb brute force; the
  7-day session means logins are rare.
- **`x-forwarded-for` spoofing**: behind Vercel/cloudflared the first hop sets it; locally
  it's absent → "local" bucket. Acceptable for this threat model; say so in a comment.
- **Middleware + login route both throttling**: implement throttling **only** in the login
  route (it's the only credential-accepting endpoint); middleware just verifies cookies.
- **Clock skew**: tokens carry absolute `exp` from server clock only — no client clocks
  involved.
