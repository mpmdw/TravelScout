## 1. Mission

Replace the `TODO(real API)` stub in the flight-status provider with a real adapter that,
given a **flight number + date**, returns live `FlightStatus` data when
`FLIGHT_STATUS_API_KEY` is set — and continues to return the deterministic mock when the key
is absent or the live call fails. The confirmation-code ("PNR not supported by public APIs")
note must survive untouched.

## 2. Context — what exists today

- `src/lib/providers/flightStatus.ts` is **fully mock**. The live seam is the block at
  `flightStatus.ts:32-39`: when `hasFlightStatus()` is true and a flight number is present,
  it currently *still* returns mock with the note
  `"Live status adapter not wired yet — showing mock data."` — that block is what you replace.
- `hasFlightStatus()` (`src/lib/config.ts:28-29`) returns `Boolean(process.env.FLIGHT_STATUS_API_KEY)`.
  `getConfig()` (`config.ts:16`) already exposes `flightStatusApiKey`.
- The mock generator `mockStatus()` (`flightStatus.ts:61-124`) is deterministic via
  `hashStr()` (`>>> 0` unsigned — there's a fixed signed-shift bug here that P2.4 writes a
  regression test for; **do not change `hashStr` or the `(h >>> 3)` usage**).
- The result envelope is `FlightStatusResult { status, source: "mock"|"live", note? }`
  (`flightStatus.ts:4-8`); the API route `src/app/api/flight-status/route.ts` passes it
  through as JSON, and the UI (`page.tsx` → `StatusSection`) reads `data.status`,
  `data.source`, `data.note`.
- `FlightStatus` domain type: `src/lib/types.ts:62-79`. Note the closed status union:
  `"On Time" | "Delayed" | "Cancelled" | "Departed" | "Landed" | "Unknown"`.
- A doc inconsistency to fix in passing: `flightStatus.ts:22` says “with FLIGHT_API_KEY set”
  — the real var is `FLIGHT_STATUS_API_KEY`. Fix the comment.
- The Amadeus adapter from P1.1 (`src/lib/providers/amadeus.ts`) is the house style to copy:
  tiny fetch-based client, descriptive `Error` messages with HTTP status, no SDK dependency.

## 3. Non-goals

- No zod validation of the route (P2.1).
- No PNR/confirmation-code live lookup — explicitly impossible with public APIs; the mock
  path and its disclaimer note stay.
- No UI changes.

## 4. Design decisions (pre-made — don't re-litigate)

1. **Provider: AeroDataBox** (via RapidAPI). Rationale: status-by-flight-number+date is a
   first-class endpoint, free tier exists, single API key header — simplest possible
   adapter. Aviationstack (free tier lacks HTTPS + is 100 req/mo) and FlightAware AeroAPI
   (no free tier) are documented as alternates but not implemented.
2. **Keep `FLIGHT_STATUS_API_KEY` as the key var** (already in `.env.example`, README, and
   `config.ts`). Add optional `FLIGHT_STATUS_PROVIDER` (default `"aerodatabox"`) so future
   adapters can slot in without renaming anything.
3. **New file for the client**: `src/lib/providers/aerodatabox.ts`, mirroring
   `amadeus.ts`'s shape (raw `fetch`, typed-enough response handling, errors as
   `Error("AeroDataBox ... (HTTP n)")`). `flightStatus.ts` stays the orchestrator
   (flag check → live → fallback), exactly like `flights.ts` does for Amadeus.
4. **Endpoint** (verify against current docs before coding —
   https://doc.aerodatabox.com/): `GET https://aerodatabox.p.rapidapi.com/flights/number/{flightNumber}/{dateLocal}`
   with headers `x-rapidapi-key: <key>` and `x-rapidapi-host: aerodatabox.p.rapidapi.com`,
   query `withAircraftImage=false&withLocation=false`. The response is an **array** of legs;
   pick the first leg (or the leg whose departure date matches).
5. **Status mapping** (AeroDataBox → our union). Anything unmapped → `"Unknown"`:

   | AeroDataBox `status` | Ours |
   |---|---|
   | `Expected`, `CheckIn`, `Boarding`, `GateClosed` | `On Time` |
   | `Delayed` | `Delayed` |
   | `Departed`, `EnRoute` | `Departed` |
   | `Arrived` | `Landed` |
   | `Canceled`, `CanceledUncertain` | `Cancelled` |
   | `Unknown`, anything else | `Unknown` |

6. **Delay computation**: `delayMin = max(0, round((revisedDep − scheduledDep) / 60000))`
   using the UTC variants of the times. If only local times exist, use them consistently
   for both operands (the difference is still correct).

**Step 2 — client (`src/lib/providers/aerodatabox.ts`, new).** Export:

```ts
export interface AdbLeg { /* the handful of fields we read — type just what you use */ }
export async function fetchFlightByNumber(
  flightNumber: string, dateLocal: string,
```

Behavior: build the URL with `encodeURIComponent(flightNumber)`; 404 → `null`; any other
non-OK → `throw new Error(\`AeroDataBox lookup failed (HTTP ${status}) ${body.slice(0,160)}\`)`
(copy the pattern from `amadeus.ts:45-48`); 10s timeout via `AbortSignal.timeout(10_000)`.

**Step 3 — orchestrator (`src/lib/providers/flightStatus.ts`).** Replace the seam at
lines 32-39 with:

```ts
if (hasFlightStatus() && flightNumber) {
  try {
    const leg = await fetchFlightByNumber(flightNumber, date);
    if (leg) return { status: mapLeg(leg, flightNumber, date, q.confirmationRef), source: "live" };
    return {
      status: mockStatus(flightNumber, date, q.confirmationRef),
      source: "mock",
      note: `No live record for ${flightNumber} on ${date}; showing mock data.`,
    };
  } catch (e) {
    return {
      status: mockStatus(flightNumber, date, q.confirmationRef),
      source: "mock",
      note: `Live status lookup failed (${(e as Error).message}); showing mock data.`,
    };
  }
}
```

Write `mapLeg(...): FlightStatus` in the same file: map airline name, origin/destination
IATA, scheduled/estimated times (ISO strings; fall back to scheduled when no revision),
status per the table above, `delayMin` per decision 6, `gate`/`terminal` if present,
`source: "live"`. If the caller passed a confirmation code **with** a flight number, carry
it through to `confirmationRef` but do not use it for lookup. Keep the existing
confirmation-only mock path (lines 41-50) byte-identical — that's invariant G4(b).

## 8. Edge cases & failure modes

- **Flight numbers with spaces / lowercase** (`ek 7`): the orchestrator already uppercases
  and trims (`flightStatus.ts:29`); also strip internal whitespace before building the URL.
- **Multi-leg responses**: pick the leg whose scheduled departure date (UTC) equals the
  query date; if none match, take the first.
- **Codeshare numbers** may return the operating carrier — fine, pass through what the API says.
- **Future dates beyond schedule horizon** → API 404 → "No live record" mock fallback (handled).
- **Missing estimated times** → estimated = scheduled, `delayMin = 0`.
