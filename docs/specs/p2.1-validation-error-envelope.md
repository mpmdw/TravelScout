## 1. Mission

Every API route validates its input with `zod` and rejects bad requests with **one
standardized error envelope** — `400 { error: string, details?: ZodIssueLike[] }` — so the
UI can always surface a friendly message and future routes have an obvious pattern to copy.

## 2. Context — what exists today

Validation is ad-hoc per route:

- `POST /api/route` (`src/app/api/route/route.ts`): manual JSON-parse try/catch → 400
  `{ error: "Invalid JSON body." }`; empty-string checks → 400; geocode miss → **404**
  `{ error: "Couldn't find a location for …" }`.
- `POST /api/flights` (`api/flights/route.ts`): JSON-parse catch + a `typeof origin?.lat
  !== "number"` check. **Notably it never validates `lng`, `name`, `query`, or `date`
  format** — a malformed Place flows into Amadeus calls.
- `GET /api/flight-status` (`api/flight-status/route.ts`): requires flightNumber-or-conf,
  else 400. No date-format validation (`date=banana` silently becomes today via the
  provider's fallback — actually it's passed through to `mockStatus` and produces
  `Date.now()`-based output; with P1.2's live adapter a bad date would 404 at the provider).
- `POST /api/geo-intel` (`api/geo-intel/route.ts`): swallows JSON errors entirely
  (`catch { body = {} }`) and defaults region. **No length cap on `region`** — a 100 KB
  region string would be interpolated straight into the Claude prompt.
- `GET /api/zones`: no input — needs no validation, but should share the envelope if it
  ever errors.
- The UI reads `data.error` as a **string** in three places (`page.tsx:109`, `:460`) and
  shows it directly. So the envelope's `error` field must stay a human-readable string —
  put machine detail in `details`.
- No `zod` in `package.json` yet.

## 3. Non-goals

- No rate limiting, no auth checks (P3.x), no response-shape changes on success paths.
- No client-side form validation work (P5.1).
- Do not convert routes to Next's typed route handlers or add middleware-level validation.

## 4. Design decisions (pre-made)

1. **Library**: `zod` v4 (`npm i zod` — current major; if v4 import surface differs from
   the snippets here, follow the installed version's idioms).
2. **Envelope**: errors are `{ error: string, details?: { path: string; message: string }[] }`.
   - `error` — short human sentence (UI-safe, ends with a period).
   - `details` — flattened zod issues (path dot-joined), present only on validation errors.
   - Status codes: `400` invalid input · `404` resource-not-found (geocode misses keep
     their current 404 + message) · `500` unexpected (added by a per-route catch).
3. **New module `src/lib/validation.ts`** exporting:
   ```ts
   export const err: (status: number, error: string, details?: Detail[]) => NextResponse;
   export async function parseJsonBody<T>(req: Request, schema: ZodType<T>):
     Promise<{ ok: true; data: T } | { ok: false; res: NextResponse }>;
   export function parseQuery<T>(url: URL, schema: ZodType<T>):
     { ok: true; data: T } | { ok: false; res: NextResponse };
   ```
   Routes then read like:
   ```ts
   const parsed = await parseJsonBody(req, RouteRequestSchema);
   if (!parsed.ok) return parsed.res;
   ```
4. **Schemas** (live in `validation.ts`, exported for tests):
   - `PlaceSchema`: `{ query: string≤300, name: string≤300, lat: number∈[-90,90],
     lng: number∈[-180,180] }` (mirror of `types.ts:8-13`; `query`/`name` may be
     `.catch("")`-defaulted — the providers only need lat/lng, but keep the type honest).
   - `RouteRequestSchema`: `{ origin: trimmed string 1..300, destination: same }`.
   - `FlightsRequestSchema`: `{ origin: PlaceSchema, destination: PlaceSchema,
     date?: /^\d{4}-\d{2}-\d{2}$/ refined to a real calendar date }`.
   - `FlightStatusQuerySchema`: `{ flightNumber?: trimmed 2..8 chars matching
     /^[A-Za-z0-9 ]+$/, date?: same date rule, conf?: trimmed 1..12 alnum }` with a
     `.refine` requiring `flightNumber || conf` (message: keep the current string
     `"Provide a flight number (and date), or a confirmation code."`).
   - `GeoIntelRequestSchema`: `{ region?: trimmed string ≤160 }` — **reject** longer
     regions with 400 rather than truncating (explicit beats silent).
   - Coerce-don't-reject where the UI sends looseness today: missing geo-intel body stays
     legal (`{}` parses; region optional).
5. **Error-message compatibility**: keep the exact current user-facing strings where the
   UI/tests may rely on them — listed in Context. New validation failures get new clear
   strings (e.g. `"Invalid request — see details."` with `details` populated).
6. **Unexpected-error catch**: each route wraps its handler body in try/catch → `500`
   `{ error: "Something went wrong on our side." }` and `console.error(e)` (until P4.3
   replaces this with the structured logger).

## 6. Acceptance criteria

- [ ] Invalid input on every route → `400` with `{ error: string, details?: [...] }`.
- [ ] Malformed JSON body → 400 envelope (not a crash, not an empty-default).
- [ ] `region` > 160 chars → 400. Bad `date` format → 400. Out-of-range lat/lng → 400.
- [ ] Geocode misses still return 404 with the existing message text.
- [ ] All success responses byte-compatible with before (G7).
- [ ] UI shows friendly messages for 400s (manually verified through the form).
- [ ] `npm run build` green; `zod` is the only new dependency.

## 7. Verification

```bash
npm run build && npm run dev & sleep 5
B='-H content-type:application/json'
curl -s -X POST localhost:3000/api/route $B -d 'not json' | python3 -m json.tool          # 400 envelope
curl -s -X POST localhost:3000/api/route $B -d '{"origin":"","destination":"x"}' | python3 -m json.tool
curl -s -X POST localhost:3000/api/flights $B -d '{"origin":{"lat":999,"lng":0,"query":"","name":""},"destination":{"lat":0,"lng":0,"query":"","name":""}}' | python3 -m json.tool   # lat 999 → 400 with details path "origin.lat"
curl -s 'localhost:3000/api/flight-status?date=2026-07-01' | python3 -m json.tool          # neither flightNumber nor conf → 400
curl -s -X POST localhost:3000/api/geo-intel $B -d "{\"region\":\"$(python3 -c 'print("x"*200)')\"}" | python3 -m json.tool  # 400
# happy paths still work:
curl -s -X POST localhost:3000/api/route $B -d '{"origin":"London","destination":"Delhi"}' | head -c 200
```

## 8. Edge cases & failure modes

- **`flightNumber` with an interior space** (`EK 7`) must validate (the provider strips it).
- **Date `2026-02-31`**: the regex alone passes — the refine must reject impossible dates
  (`new Date(s)` round-trip check).
- **Numbers as strings** (`"lat": "51.5"`): reject (no coercion) — the UI always sends real
  numbers from a prior `/api/route` response.
- **Extra unknown keys**: allow (zod default strip/passthrough is fine); don't `.strict()`
  — forward-compat for fields like a future `force` flag.
